The queue clears itself.

plungarr checks Sonarr, Radarr and SABnzbd every five minutes. It finishes the imports that only needed a nudge, clears the downloads that can never import, removes dead posts wedged at the head of the SABnzbd queue, and tells you about anything that genuinely needs a decision. It never touches a library file.

What happens every cycle

Every stuck download has a reason. For the reasons plungarr recognises, it does what you would do by hand, and the policy for each is a setting.

SituationWhat plungarr does
Completed download blocked on a technicality: “matched to series/movie by ID”, “unable to determine if sample”Verifies every file maps to the exact series or movie that was grabbed, then force-imports. A mapping mismatch is never imported.
Download that is not an upgrade for the existing file, reported on the queue row or only on the files inside itNOT_UPGRADE_ACTION, default discard: remove and blocklist, keep the library file
Archive the download client never extractedARCHIVE_ACTION, default replace: remove, blocklist, search for a different release
Dangerous or executable file in the downloadDANGEROUS_FILE_ACTION, default replace
File flagged as a sampleSAMPLE_ACTION, default notify, because short-form shows trip the sample detector on real episodes
“No files found are eligible for import”, or a season pack that is one video fileRemove, blocklist, search for a replacement
Dead usenet post at the head of the SABnzbd queue: under 5 MB of progress in 45 minutes, or most articles missingRemove through the arr that grabbed it, blocklist, search again. One per cycle, so live downloads keep going.
Anything elseLogged, sent to your notifications if configured, and left alone. It never guesses.

What it never does

  • Never deletes a library file. The library review is report-only, always.
  • Never imports a file that maps to a different series or movie than the one that was grabbed.
  • Never acts on a state it does not recognise. Unknown means notify.
  • Never races an import in progress: transitional items must be seen stuck across two cycles first.
  • DRY_RUN=true logs every intended action and sends nothing.

Twice a day, it looks further

  • Chronic failures. Every six hours it reads the arrs' history and flags any episode or movie with three or more failed grabs and no successful import since. That is your short list of things that need a human to pick a release.
  • Suspect library files. Once a day it reports an MKV with no media info, a tiny file with no metadata, or a very low bitrate for its length. Each file is reported once. Nothing is deleted.

It tells you, on your schedule

Optional digests to Discord, Slack, ntfy, Gotify, Apprise or any JSON endpoint. Each category, from “needs attention” to “what plungarr did this month”, has its own cadence: immediate, daily, weekly, monthly or off. Items still waiting on you are re-sent after a week so nothing sits forgotten. Notifications.

Small on purpose

One Node file, no dependencies, MIT licence. It talks to Sonarr, Radarr and SABnzbd over their own HTTP APIs and needs nothing else. Any number of Sonarr and Radarr instances can be configured in one container. There is no web UI, by design: the policy is set once, and the log and digests are the interface. Why.
